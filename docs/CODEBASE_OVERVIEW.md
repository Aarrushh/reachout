# ReachOut — Codebase Overview

*Written 2026-08-05, from the code on `main` at `d8f48bd`. Every claim below
was checked against a file, not against a doc. Where a doc disagrees with the
code, this document says so and names the file.*

This is the orientation document for an engineer joining the project. It
covers both phases: **v1**, the shopper pipeline and its live API, and **v2**,
the demand service and the retail dashboard. It explains what the code does in
coding logic — inputs, outputs, who calls what, what halts what — and why the
odd-looking parts are shaped the way they are.

Read §1 and §2 before touching anything. §10 tells you which files lie.

## 1. What the product is

A shopper types what they need in plain language — *"algo para el dolor de
cabeza"* — and the system answers with the shops near them that have it **in
stock right now**, ranked by distance and price. Not by ad spend, not by a
marketplace's take rate. The output is a factual list: shop name, address,
distance, item, price, units on hand. There is no editorial content anywhere
in the pipeline, and `reachout/stages/04-format-results/prompt.md` says so
explicitly — no "community cards", no story, no copy about the shop.

Madrid is the test market. The shop identities are **real**, ingested from
OpenStreetMap via Overpass (`reachout/scripts/osm_ingest.py`) — 3328 shops in
the committed SQLite database. The inventory on those shelves is **synthetic**,
generated by `reachout/scripts/inventory_seeder.py` from
`reachout/data/sku_catalog.json` and moved around continuously by
`reachout/scripts/inventory_simulator.py`. That split is deliberate: the hard
part to fake convincingly is geography, and the hard part to obtain honestly is
live stock, so the project buys the first for free and admits the second is a
simulation.

### The strategic problem v2 exists to solve

The product has a two-sided cold start, and it is the asymmetric kind. A
shopper only gets value if merchants have joined and are publishing live stock.
A merchant only gets value if shoppers are already searching. Neither side
moves first for free, and the merchant side is the expensive one — it needs a
POS integration or a person updating a feed.

The v2 bet is to **build the supply side first, using data that requires zero
merchant participation.** The demand service ingests public Google Trends
search interest for Madrid retail terms, turns it into per-keyword rising /
falling / flat signals, and joins those signals against whatever store and
product data already exists to produce a per-store recommendation: *"interest
in `bebidas energéticas` is rising in Madrid; you have 7 products in that
category in stock."*

That is a thing you can put in front of a shopkeeper on day one, before they
have installed anything, before they have signed anything, and before a single
shopper has used the app. It is the wedge. If it works, the merchant
relationship starts with the platform *giving* the merchant information rather
than asking them for an integration — and the live-stock feed becomes the
second conversation instead of the first.

That ordering is the whole bet, and it is why `demand/` was built before the
consumer app was finished.

## 2. The one design rule, and where it is enforced

> **Work that must be exact is pure Python. AI only touches language.**

Stated in `reachout/CLAUDE.md` and repeated in `demand/CLAUDE.md`. The
reasoning is a hallucination-blast-radius argument: a model that invents a
friendly phrasing costs you nothing; a model that invents a stock level, a
distance, a price, or a trend direction has corrupted the only thing the
product sells.

### Where the line physically sits

| Path | AI? | Why |
|---|---|---|
| `reachout/scripts/` | **Never** | Distance, matching, stock reads, DB writes, GeoJSON projection |
| `reachout/stages/01-parse-query/` | **Optional** | Free text → structured intent |
| `reachout/stages/04-format-results/` | **Optional** | Item-name casing only |
| `reachout/api/search.py`, `chat.py` | **Yes** | Gemini: query intent extraction, shopkeeper replies |
| `demand/` (entire tree) | **Never** | No agentic stage exists here at all |

Two things are worth noticing.

First, **both v1 agentic stages default to deterministic code and run fully
without a key.** `reachout/agent/query_parser.py:177` only calls the model if
you pass `use_llm=True` *and* `ANTHROPIC_API_KEY` is set; otherwise it runs
`_rule_based_parse`, a longest-match scan over a committed bilingual synonym
table (`query_parser.py:30-74`). The comment on that table is the rule in
miniature: *"This is plain data, not intelligence: the parser selects from it,
it never extends it."* If the LLM path throws, it falls back to rules
(`query_parser.py:182-184`). If the result fails its schema, it falls back
again to `_fallback_intent` — the user's own words with stopwords removed,
nothing invented (`query_parser.py:162-174`).

Second, **`demand/` has no agentic stage because it never needed one.**
Retailer-facing copy is generated from fixed Python f-string templates in
`demand/scripts/recommend.py:105-113`. There is exactly one Spanish sentence
per direction. A language model would produce nicer prose and would also be
capable of writing *"stock up now"* under a `low`-confidence signal, which is
precisely the failure the whole service is designed to make impossible.

### The enforcement mechanism

Schemas, not code review. Every payload that crosses a module boundary is
validated against a JSON Schema with `"additionalProperties": false`. There are
16 such schemas in `reachout/shared/schemas/` and 5 in `demand/shared/schemas/`.
`additionalProperties: false` is the hallucination gate — the schema
descriptions say so in those words, e.g.
`reachout/shared/schemas/picks_response.schema.json`.

A concrete rejection. `reachout/tests/test_result_formatter.py:106-109` takes a
valid `ranked_shops` payload, adds one field to a result —

```python
llm_output["results"][0]["community_note"] = "A beloved neighbourhood farmacia..."
```

— and asserts that `format_results` discards the entire LLM output and returns
the deterministic build instead. The schema has no `community_note` property
and forbids extras, so the smuggled editorial content cannot reach a response
body. The rejection is also logged as a `formatter_llm_rejected` event
(`reachout/agent/result_formatter.py:149`).

A second, sharper example lives in the picks contract:

```json
"generated_by": { "const": "deterministic" }
```

`GET /api/picks` cannot describe itself as anything else. The claim is pinned
by the contract, not by the endpoint's honesty.

### One place the gate is weaker than the comment claims

`reachout/agent/result_formatter.py:11` states that any deviation in the LLM
pass — *"a smuggled field, a changed number, anything"* — discards the output.
The first half is true. The second is not. `format_results` validates
`llm_output` against the schema and, if it passes, returns it **wholesale**
(`result_formatter.py:147-152`). The schema constrains *shape*, not *values*.
A model that returned the same structure with `"price": 1.00` on every row
would pass validation and be served.

This is currently unreachable in production — nothing sets `use_llm=True` on
the API path (`reachout/api/server.py:202` calls `run_pipeline.run` without it)
— but it is a live trap for whoever turns that flag on. **The fix is small:**
compare `llm_output` to `deterministic` field-by-field and accept only
`item_name` differences, rather than trusting schema validation to police
values it was never asked about.

## 3. The v1 runtime

### 3.1 The 01→05 batch pipeline

`reachout/run_pipeline.py` is the orchestrator, and it is the ICM idea
expressed as code: the folder numbering under `reachout/stages/` **is** the
execution order.

| Stage | Module | Kind | Input | Output | Schema on the edge |
|---|---|---|---|---|---|
| 01 parse-query | `agent/query_parser.py` | Agentic | free text | `intent.json` | `search_intent.schema.json` |
| 02 geo-resolve | `scripts/geo_resolve.py` | Pure | intent + lat/lng/near/radius | `geo_shops.json` | `geo_shops.schema.json` |
| 03 match-and-ping | `scripts/search_engine.py` | Pure | intent + geo_shops + live DB | `matches.json` | `stock_matches.schema.json` |
| 04 format-results | `agent/result_formatter.py` | Agentic | matches | `ranked_shops.json` | `ranked_shops.schema.json` |
| 05 map-render | `scripts/map_render.py` | Pure | ranked_shops + geo_shops | `shops.geojson` | `map_geojson.schema.json` |

**The non-obvious part is the write-then-read-back round trip.** Look at
`run_stage_01` (`run_pipeline.py:121-126`): it calls `_write_stage_output`,
which validates and writes, and then immediately calls `_read_stage_output`,
which re-reads the file from disk and validates it *again* before returning it.
Every stage does this. It looks redundant and is not: the docstring at
`run_pipeline.py:8` explains that this is what makes a corrupted intermediate
file **halt** the pipeline rather than being silently patched up in memory. The
file on disk is the contract, so the file on disk is what gets checked.

**Where the halt lives.** `_halt_if_not_ok` (`run_pipeline.py:89-93`) raises
`PipelineError` on any `status` other than `"ok"`, and `run()` calls it after
every one of the five stages (`run_pipeline.py:196, 202, 207, 212`). Stage 05
has no status field — GeoJSON has no room for one — so it uses an error-sidecar
convention instead: `map_render.write_output` returns `(geojson, error)` and
the orchestrator raises on a non-`None` error (`run_pipeline.py:184-186`).
`PipelineError` propagates to the CLI as exit code 1, and to the API as a
`422`.

**Stage 03 is the heart, and it is the strictest about invention.**
`search_engine.py` reads each candidate shop's live in-stock rows from SQLite,
keeps items whose name or category **whole-word** matches a keyword
(`_matches`, `search_engine.py:26-33` — tokenised, so `usb` does not match
`usbc`), gates by `category_hints` against the shop's full category list, then
ranks nearest → most matching stock → cheapest. Distances are **copied
unchanged** from stage 02; they are never recomputed and never estimated.

### 3.2 The live layer

`reachout/api/server.py` (397 lines) is a thin read-only wrapper. Its module
docstring is accurate: no business logic lives there. Two design points matter.

**Per-request temp directories.** `_run_pipeline` (`server.py:200`) creates a
fresh `tempfile.mkdtemp()` as the stage `output_root` for every request and
deletes it in a `finally`. Without this, concurrent requests would read and
clobber each other's stage files, because the stage folders are real
directories on disk, not per-request state. This is the price of the
file-on-disk contract, and it is paid here.

**Two search implementations on one path, split by method** (`server.py:86-96`):

- `GET /api/search` — the v1 pipeline, schema-validated, SQLite.
- `POST /api/search` — the v2 Supabase path in `api/search.py`: Gemini Flash
  Lite extracts intent *concurrently* with `gemini-embedding-001` embedding
  the raw query (`search.py:118-121`), then a `match_products` pgvector RPC,
  then a deterministic re-rank that boosts exact name match (+0.30), token
  overlap (+0.15 × ratio), brand hint (+0.10) and in-stock (+0.05)
  (`search.py:72-85`).

They do not clash — different HTTP methods. Decision S6 keeps the frontend on
the `GET` pipeline path; the `POST` path stays mounted but **unused by the
frontend**. That is worth knowing before you spend an afternoon debugging why
your pgvector changes have no visible effect.

### 3.3 The simulator, the bus, and SSE

When `REACHOUT_SIM=1`, the FastAPI lifespan starts an `AsyncIOScheduler` firing
`tick_once` every 2 seconds with 1 second of jitter (`server.py:60-64`). Each
tick runs `inventory_simulator._tick(conn)` in a worker thread
(`server.py:42-43` — `asyncio.to_thread`, because the simulator is synchronous
SQLite), commits, and if the tick produced an event, publishes it to the bus.

`api/event_bus.py` is an in-memory pub/sub over a set of `asyncio.Queue`s,
`maxsize=100`. Its backpressure policy is explicit and worth reading
(`event_bus.py:57-76`): a full subscriber queue gets its **oldest** event
dropped to make room for the newest. A slow browser tab degrades to "you missed
some stock changes", never to "the simulator blocked". `to_stock_event`
(`event_bus.py:13-38`) shapes the raw simulator dict into the
`stock_event.schema.json` shape and **raises** if it fails validation — an
invalid event is not published at all.

`GET /api/inventory/stream` (`server.py:370-397`) subscribes, emits a `hello`
frame, then loops with a 15-second `asyncio.wait_for`; on timeout it emits an
SSE comment keep-alive (`": keep-alive\n\n"`) so proxies do not close the
connection. It sets `X-Accel-Buffering: no` for the same reason.

### 3.4 Region assignment, and why scoped SSE needs it

`GET /api/inventory/stream?region=<id>` filters events server-side
(`server.py:382-383`). For that filter to mean anything, every shop must carry
a `region_id` — which is what `reachout/scripts/region_seeder.py` provides.
`seed_regions` slugifies the Madrid gazetteer into region rows; `assign_shops`
(`region_seeder.py:47`) assigns each shop to the **nearest region centroid
within 1.2 km**, and explicitly sets `region_id = NULL` otherwise.

The docstring is honest that nearest-centroid is a crude proxy for real barrio
polygons, chosen to avoid a `shapely` dependency. The consequence is worth
stating plainly, because it is not written down anywhere else: **a shop more
than 1.2 km from every centroid has `region_id = NULL`, so its stock events
carry `region_id: null` and are invisible to every scoped subscriber.**
`stock_event.schema.json` permits the null, so nothing errors — the events just
silently never match a region filter. An unscoped subscriber sees them fine.

## 4. The v2 demand service, module by module

`demand/` is a **second ICM workspace** — its own `CLAUDE.md`, `CONTEXT.md`,
`_config/`, `shared/schemas/`, and its own FastAPI app on its own port. Not a
router bolted onto `reachout/api/server.py`. §8 explains why.

The chain, in read/write order:

```
_config/seed_keywords.json  ─┐
                             ├─> ingest/keywords.py  ──> keyword universe (list[str])
public.products.category    ─┘
                                        │
                                        v
                            ingest/trends_client.py  ──> raw captures
                                        │
                                        v
                            ingest/snapshot_store.py ──> demand.trend_snapshots
                                        │
                                        v
                            scripts/compute_signals.py ──> demand.demand_signals
                                        │
                                        v
                            scripts/recommend.py     ──> demand.recommendations
                                        │
                                        v
                            api/app.py               ──> HTTP
```

`scripts/run_ingest.py` is the batch entrypoint that drives steps 1–5 in one
process.

### 4.1 `ingest/keywords.py` — the keyword universe

`build_universe(supa_client)` reads `_config/seed_keywords.json` (47 curated
Spanish Madrid-retail terms: `abanico`, `agua mineral`, `aspirinas`, …) and
unions it with the distinct non-empty `category` values from
`public.products`. Deduped case-insensitively with **seed keywords winning
ties**, sorted deterministically, capped at 100.

The critical function here is `normalize_keyword` (`keywords.py:10-27`) — strip
and lower — and its docstring is the single most valuable comment in the
service:

> Before this existed the map was keyed lower-case and the lookup was an exact
> match against the original casing, so in production the lookup missed on
> every keyword whose category was not already lower-case and **every signal
> row was written with `category: None`.**

The universe deliberately preserves each keyword's **original casing**, because
that is what gets sent to Google Trends and Trends is case-sensitive about what
it echoes back. So the universe and the category map are in different casings
by design, and every join between them must pass through `normalize_keyword` on
**both sides**. It is applied in three places: dedupe in `build_universe`
(`keywords.py:64,69,74`), map construction in `run_ingest.run_chain`
(`run_ingest.py:146`), and lookup in `compute_signals` (`compute_signals.py:258`).

A `category: None` signal is not a cosmetic defect. `build_recommendations`
skips any signal without a category (`recommend.py:55-57`), so the bug silently
produced **zero recommendations** from a full ingest.

### 4.2 `ingest/trends_client.py` — the provider

`TrendsProvider` is a `Protocol` with two methods: `interest_over_time` and
`interest_by_region`. Two implementations: `TrendspyProvider` (live scrape) and
`FixtureProvider` (replays committed JSON). `get_provider(name)` selects.

Three hard-won constraints are encoded here, each with the date it was learned:

**Five terms per request** (`trends_client.py:64-70`). Verified live
2026-08-03: six terms returns `400` from Google's timeseries endpoint, five does
not. The universe is ~49 terms, so a single request was never going to work —
and no test caught it, because every test drives a mock that accepts any number
of terms. That comment is the most useful kind: it names the class of bug the
test suite structurally cannot see.

**Anchor rescaling** (`_rescale_to_anchor`, `trends_client.py:97-132`). Google
re-normalises every request independently — whatever term peaks *inside that
request* becomes 100. So 80 in one batch and 80 in another are not the same
amount of interest, and `compute_signals` ranks across the whole universe.
Ranking unreconciled batches would be comparing two scales and calling the
result a rank. The fix is the standard one: carry a shared anchor term in every
batch (`KEYWORDS_PER_BATCH = 4`, one slot spent on the anchor) and multiply
each batch by the factor that puts its anchor back on the reference batch's
level. When the anchor reads zero for a whole batch there is no factor, and
those keywords are **dropped rather than emitted on an unknown scale** — *"a
missing keyword is honest, a mis-scaled one is a fabricated number."*

**Lazy imports** (`_load_trendspy`, `trends_client.py:36-61`). `pandas` and
`trendspy` are imported inside the one function that scrapes, not at module
scope, so `FixtureProvider` and the entire test suite work on a machine that
has neither. That is the normal state of a Jules VM (§8). The failure message
names both fixes: install the requirements, or re-run with `--provider fixture`.

### 4.3 `ingest/snapshot_store.py` — the write

`store_snapshots(rows, supa_client)` validates each row against
`trend_snapshot.schema.json`, attaches `captured_date`, and upserts on
`keyword,geo,timeframe,captured_date`.

**The order is load-bearing** and the docstring says so in capitals: validation
happens on the row **as handed in**, *before* `captured_date` is attached.
`captured_date` is a DB-only column absent from the schema, and the schema is
`additionalProperties: false`, so validating the row that is actually written
would fail every single time. See §4.6.

### 4.4 `scripts/compute_signals.py` — the derivation

Pure Python, deterministic by contract: the same snapshots in produce
byte-identical rows out, in the same order, regardless of arrival order or
re-run count. There is no `uuid4()` anywhere in the file, on purpose.

**Windowing.** Points are bucketed into ISO weeks (Monday–Sunday). Values are
grouped **by capture, not merged** (`compute_signals.py:145-173`). The comment
explains why: two requests' values for the same week are on different Google
normalisation scales, so averaging 50 and 90 into 70.0 produces a number that
means nothing. Within one capture the scale is shared, so multiple daily points
in a week *are* averaged. Across captures, **the most recent capture wins** —
deterministic, and the freshest normalisation is the one the rest of that
series is expressed in.

**Direction** (`compute_signals.py:62`): `rising`/`falling` only at or beyond
±15% week-over-week; strictly inside the band is `flat`. The boundary is
inclusive.

**Rank** (`compute_signals.py:262-267`) is computed per `(window, geo)`, never
globally. ES-CT and ES-MD are separate markets on separate 0–100 scales, so
ranking them against each other would be meaningless *and* would make the
output depend on which geos happened to be in the batch.

**Confidence** (`compute_signals.py:66-80, 228-251`) — see §4.7.

### 4.5 `scripts/recommend.py` — the join

For each signal with a non-null category, read `public.products` filtered to
that category, count in-stock SKUs per store, and emit one recommendation per
store. Action is a fixed decision table (`recommend.py:96-103`):

| Condition | Action |
|---|---|
| `rising` and ≥3 in-stock products | `feature_in_window` |
| `rising` and confidence ∈ {high, medium} | `stock_up` |
| otherwise | `watch` |

Two details that read as pedantry and are not:

`PRODUCT_COLUMNS = "store_id,stock_qty"` (`recommend.py:12`) — never
`select("*")`, because `products` carries a **768-dimension embedding vector**
that would be dragged over the wire once per signal in the batch.

`stock_qty = p.get("stock_qty") or 0` (`recommend.py:81`) — `or`, not
`.get(..., 0)`. The default of `.get` only fires when the *key* is absent, and
PostgREST returns a NULL column as the key present with value `None`.
`None > 0` is a `TypeError` that has already 500'd an endpoint in this repo.

### 4.6 `demand.trend_snapshots.captured_date` — the column that must never be returned

The obvious implementation is a generated column:

```sql
captured_date date GENERATED ALWAYS AS (captured_at::date) STORED
```

Postgres rejects this at `CREATE TABLE` with *"generation expression is not
immutable"*. The `timestamptz → date` cast depends on the session `TimeZone`
setting, so it is declared **STABLE, not IMMUTABLE**, and generated columns
require IMMUTABLE. This is not version-gated; it always fails
(`demand/data/schema.sql:24-41`). The usual workaround — a hand-written SQL
function force-marked IMMUTABLE against a fixed `'UTC'` zone — adds a schema
object outside this file's three tables for the sake of one column.

So it is a **plain application-set column**: the writer derives it from
`captured_at[:10]` and includes it in every upsert payload.

The consequence propagates through the whole service. `captured_date` is not in
`trend_snapshot.schema.json`, and that schema is `additionalProperties: false`.
Therefore:

1. It must **never appear in a response body**.
2. Nothing may `SELECT *` on `demand.trend_snapshots` — every read must name
   its columns explicitly (`demand/api/app.py:96-98`).
3. Nothing may feed a `select("*")` result back into `compute_signals`, whose
   docstring says exactly that (`compute_signals.py:128-134`).

`demand/tests/test_api.py` asserts that no `select` in `app.py` is `"*"`. That
is the guard, and it is a good one — the constraint is invisible at the call
site otherwise.

### 4.7 Confidence tiers, and the window that made `high` reachable

Fixed thresholds in `compute_signals.py:62-80`, applied in `:228-251`:

| Tier | Requires |
|---|---|
| `low` | any gap in the weekly series → immediate `low`, no exceptions |
| `medium` | ≥4 weekly windows **and** `interest_avg ≥ 10.0` |
| `high` | ≥8 weekly windows **and** `interest_avg ≥ 20.0` **and** direction stable across 3 consecutive windows |

The subtle bug this encodes: `run_ingest.py` originally fetched `today 1-m`,
which is about **four** weekly windows. `HIGH_MIN_WINDOWS` is 8. So the `high`
tier was **structurally unreachable in production** — no ingest could ever
produce one. And it was invisible, because `MEDIUM_MIN_WINDOWS` is 4, so
`medium` rows kept appearing and the output looked healthy.

The fix was to move the ingest window, not the threshold: `INGEST_TIMEFRAME =
"today 3-m"` (`run_ingest.py:28`), roughly 13 weekly windows per capture. The
threshold is the spec; the ingest window was the side that was wrong. Both
constants carry comments pointing at each other, so narrowing the window again
should trip an alarm in review.

### 4.8 The uuid5 natural-key scheme

Three functions mint ids, and all three are pure functions of the row's natural
key, hashed under one namespace:

```python
DEMAND_ID_NAMESPACE = uuid.uuid5(uuid.NAMESPACE_DNS, "demand.reachout")
                    # == 4ee47505-4a32-5e02-bc8a-d6fb147fa272
```

| Function | Natural key | Matching dedupe index |
|---|---|---|
| `snapshot_id` (`run_ingest.py:33`) | `trend_snapshot\|kw\|geo\|timeframe\|captured_date` | `trend_snapshots_dedupe_idx` |
| `signal_id` (`compute_signals.py:42`) | `demand_signal\|kw\|geo\|window_start\|window_end` | `demand_signals_dedupe_idx` |
| `recommendation_id` (`recommend.py:27`) | `recommendation\|store_id\|signal_id` | `recommendations_dedupe_idx` |

Each id hashes **exactly the tuple its dedupe index enforces**, which is also
exactly the tuple passed to PostgREST as `on_conflict`. `uuid5` output is a
real RFC-4122 UUID, so it satisfies `format: uuid` in the schemas.

**What this buys.** Idempotency in row *identity*, not merely in row *count*.
What it replaced was a `uuid4()` scheme that forced a compensating read of the
whole table on every run just to copy the previous run's ids back over the new
ones — and any row that read missed came back with a fresh id, which then
leaked into the `snapshot_ids` provenance column of every signal derived from
it. Under `uuid4`, the row count stayed stable across re-runs while every row's
identity churned. As `recommend.py:37` puts it: *"the idempotency requirement
is about rows, not counts."*

The id is now a function of the data, so re-running a day's capture recomputes
the id it already wrote, and nothing has to be looked up. `run_ingest.py:75-77`
and `:151-156` both note that the read-back is gone.

### 4.9 The two-schema client

`get_client()` (`demand/api/app.py:154-162`) is the **only** Supabase client
constructor in the workspace, and it binds `ClientOptions(schema="demand")`.

That makes `client.table("trend_snapshots")` resolve to
`demand.trend_snapshots` — convenient for the three tables this service owns,
and a trap for everything else. `public.products` and `public.stores` belong to
the v1 service, so every cross-schema read must say so explicitly:

```python
supa_client.schema("public").table("products").select(...)
```

Three call sites do this: `keywords.py:49`, `recommend.py:59-66`,
`run_ingest.py:130`, plus the analytics live path at `app.py:596-600`.

**What breaks when someone forgets:** a bare `.table("products")` asks
PostgREST for `demand.products`. `demand/data/schema.sql` creates exactly three
tables and `products` is not one of them, so the call fails — not with a
helpful "wrong schema" but with a PostgREST 404 that reads like the table does
not exist anywhere. Both `keywords.py` and `recommend.py` carry the explanation
in a docstring or a module constant precisely because the error message will
not tell you.

### 4.10 Why a recommendation cannot exist without a confidence and a caveat

`recommendation.schema.json` marks `confidence` and `caveat` as required and
non-empty. `demand.recommendations` marks both columns `not null`
(`schema.sql:105-106`). `build_recommendations` validates every row before
returning it (`recommend.py:128`). The caveat is one fixed string:

> *Basado en interés de búsqueda en Madrid, no en compras reales.*
> ("Based on search interest in Madrid, not on actual purchases.")

There is no code path that produces a recommendation without both. And the UI
side is not allowed to hide them: `frontend/src/components/retail/charts/ChartPanel.tsx`
renders the confidence chip and the caveat as **text in the flow** — not a
tooltip, not a `title` attribute, not behind a hover. U7's browser run asserts
this at 1280px and at 375px, and asserts that the retail subtree contains zero
`title` attributes.

This is the project's cardinal honesty rule, and it is enforced at four layers:
schema, DB constraint, server validation, and a browser test.

### 4.11 The analytics endpoint's confidence, derived and never asserted

`GET /demand/api/analytics` returns three chart segments, each with its own
confidence label. Two different derivation rules, because the two kinds of
segment have two different failure modes:

`_weakest_confidence` (`app.py:286-306`) — for `top_movers`, whose inputs
(`demand_signals.confidence`) carry their own deterministic label. **A segment
is exactly as trustworthy as its least trustworthy input.** Any row whose label
is missing or outside the enum yields `low`; an unlabelled input cannot raise a
segment's confidence. The docstring records what this replaced: the endpoint
used to **hardcode `"high"`** while every contributing row said `low`.

`_census_confidence` (`app.py:309-327`) — for `category_mix` and
`stock_out_risk`, which come from `public.products` and carry no confidence of
their own. These are a census, not an inference, so the only thing that can
make them untrustworthy is not having seen the whole population: read complete
→ `high`, read truncated at the cap → `low`. Deliberately conservative at the
boundary; exactly `cap` rows counts as truncated.

A related fix worth knowing about, because it is the shape of error this
codebase is most prone to: `stock_out_risk` used to compute `at_risk = total //
2` over a query **that never selected `stock_qty` at all** (`app.py:501-507`).
Every even-sized category reported exactly 50% risk — a plausible-looking
number with no input whatsoever. It is now a count of SKUs at or below
`STOCK_OUT_QTY_THRESHOLD = 2`, and `ANALYTICS_PRODUCT_COLUMNS` selects the
column.

### 4.12 The env-loading fix

`demand/api/app.py:67`:

```python
load_dotenv(Path(__file__).resolve().parents[2] / "reachout" / ".env")
```

At **import time**, not inside a function. One credentials file for the whole
repo — the same `reachout/.env` that `reachout/api/supa.py` loads — rather than
one per service.

The reason it lives in `app.py` specifically is that `get_client()` is the
single Supabase client choke point, and `demand/scripts/run_ingest.py:10`
imports it. So loading here covers **both** the API process and the CLI chain.
Before this, the chain only ran if you exported both variables into the shell by
hand.

Two properties of `load_dotenv` make this safe: it does not overwrite an
already-set variable (so an explicit `export` still wins), and a missing file is
a no-op rather than an error. The second is what keeps the Jules-VM rule intact
— those VMs hold no keys, and the entire 158-test demand suite runs on fakes and
fixtures with no `.env` present. That is also why the `trendspy`/`pandas`
imports stay lazy (§4.2): a VM with no live dependencies must still be able to
run every test green, or the offload model in §8 collapses.

## 5. Data model

### 5.1 The three demand tables

All in `demand/data/schema.sql`, idempotent (`create ... if not exists`
throughout).

**`demand.trend_snapshots`** — raw captures.
`id uuid pk, keyword text, geo text, timeframe text, provider text,
captured_at timestamptz, captured_date date, series jsonb,
region_breakdown jsonb (nullable)`.

- `trend_snapshots_dedupe_idx` unique on `(keyword, geo, timeframe,
  captured_date)` → **re-running the same day's capture upserts, never
  duplicates.** Deliberately a bare-column index, not an expression index, so
  the upsert can pass it straight to PostgREST as `on_conflict`.
- `region_breakdown` is nullable and the ingest stores `None`, not `[]`, when a
  breakdown could not be fetched (`run_ingest.py:106-109`). An empty list would
  claim *"we asked and Madrid has no regional interest"*, which is a different
  statement from *"we could not get a breakdown."*

**`demand.demand_signals`** — derived.
`id, keyword, category (nullable), geo, window_start date, window_end date,
interest_avg numeric, delta_pct numeric, direction text, rank int,
confidence text, snapshot_ids uuid[], computed_at timestamptz`.

- `demand_signals_dedupe_idx` unique on `(keyword, geo, window_start,
  window_end)` → **one signal per keyword per geo per window**, so recomputing
  a window updates rather than inserts.
- There is **no barrio column**, on purpose (`schema.sql:62`): the geo scope is
  ES-MD, and without a sub-region column nothing downstream can pretend to
  resolve below it.
- **No CHECK constraints** on `direction`, `confidence`, `interest_avg` or
  `rank`. `_validate_response` (`app.py:226-242`) exists precisely because a
  contract-violating row is reachable in production, not hypothetical.

**`demand.recommendations`** — retailer-facing.
`id, store_id uuid → public.stores(id), signal_id uuid → demand.demand_signals(id),
headline, body, action, confidence, caveat, created_at`.

- `recommendations_dedupe_idx` unique on `(store_id, signal_id)` → **at most one
  recommendation per store per signal**, because the action rules are a
  deterministic function of `(signal, store composition)`.
- The FK to `public.stores` is the one hard coupling between the two services.
  It is a foreign key across Postgres schemas in the same database, which works
  fine — but it means the demand service cannot be extracted to its own
  database without replacing that constraint with something else.

### 5.2 RLS is off, and the service key is the only gate

`schema.sql:120-125` disables row-level security on all three tables. This
follows decision D2: no auth in the POC. There is no `demand.retailers` table,
no JWT verifier, no GRANT block, and `store_id` on the API is a **filter
parameter, not an authorization subject** (`app.py:3-5`).

**State the risk plainly:** with RLS off and no auth, the `service_role` key is
the *only* thing standing between the internet and full read/write on the
demand schema. Anyone holding that key can write recommendations, and the
service has no way to tell them apart from the ingest job. `docs/TRACKER.md`
row V1a is explicit that the grant must go to `service_role` **only, never
`anon`** — granting `anon` would put write access on the public internet with
nothing in front of it.

This is an acceptable POC posture. It is not an acceptable posture the day a
real merchant's data lands in it, and the reversal path is preserved verbatim in
`docs/IMPLEMENTATION_PLAN.md` §3.4 (the full JWT + `demand.retailers` + RLS
design) — restoring it inserts a `Depends` and changes no endpoint signature.

### 5.3 Deployment reality — three manual steps, only one of which is in the file

This is the part that will waste your afternoon if nobody tells you.

1. **DDL cannot be applied by the app's key.** Probed and recorded: the
   available `sb_secret_…` key cannot execute DDL. PostgREST does no DDL, and
   the Management API rejects it with a 401 (it needs an `sbp_` personal access
   token). So `demand/data/schema.sql` is **pasted by hand into the Supabase SQL
   editor.** `docs/TRACKER.md` M3 is tagged `[MANUAL/FOUNDER]` for this reason —
   the stall is visible rather than silent.

2. **The `demand` schema must be added to the Data API's exposed schemas.**
   Settings → API → Data API → Exposed schemas → add `demand`. The client sends
   `Accept-Profile: demand`, and PostgREST refuses any schema not on that list.
   Skip this and **every call 404s with the tables sitting right there.**

3. **A new schema carries zero privileges.** `grant usage on schema demand to
   service_role`, `grant all on all tables in schema demand to service_role`,
   and `alter default privileges in schema demand grant all on tables to
   service_role`. Skip this and **every call is a 42501 permission error.**

Only step 1 exists in the SQL file. Steps 2 and 3 are dashboard actions written
down only in `docs/TRACKER.md` row V1a. That is a documentation weakness worth
fixing: they belong in a comment at the top of `schema.sql`, where the person
running the DDL will actually see them.

## 6. The API surface

on `:8001` (`VITE_DEMAND_API_BASE`). Both CORS-allow `localhost:5173` and
`*.netlify.app` only (`server.py:77-83`, `app.py:190-195`).

### 6.1 Shopper API — `reachout/api/server.py`

| Endpoint | Params | Validated against | Failure |
|---|---|---|---|
| `GET /api/health` | — | `health_response.schema.json` | Missing tables are swallowed (`sqlite3.OperationalError` → counts stay 0) |
| `GET /api/search` | `q, near\|lat+lng, radius, region, page, page_size` | `ranked_shops` or `search_page` when paginated | `PipelineError` → 422; bad param combo → 400; unknown region → 404 |
| `GET /api/search.geojson` | same, no paging | `map_geojson` (in-pipeline) | as above |
| `GET /api/shops.geojson` | — | `shops_geojson.schema.json` | 500 on schema failure; `Cache-Control: max-age=3600` |
| `GET /api/inventory` | `region, page, page_size, in_stock` | `inventory_response.schema.json` | unknown region → 404 |
| `GET /api/regions` | — | `regions_response.schema.json` | cacheable, 1 hour |
| `GET /api/inventory/stream` | `region` | events pre-validated by `to_stock_event` | SSE, 15s keep-alive |
| `GET /api/products` | `neighbourhood, category, limit, offset` | *(none)* | Supabase error → 502 |
| `GET /api/stores` | `neighbourhood` | *(none)* | Supabase error → 502 |
| `GET /api/neighbourhoods` | — | *(none)* | — |
| `POST /api/search` | `{query, neighbourhood}` | *(none)* | Gemini error → 502; RPC error → 502 |
| `POST /api/chat` | `{store_id, message, history}` | *(none)* | — |
| `GET /api/picks` | `neighbourhood, limit≤50` | `picks_response.schema.json` | Supabase error → 502; schema failure → 500 |

Note the split: **the pipeline endpoints are schema-validated, the Supabase v2
endpoints are not.** `/api/products` and `/api/stores` return whatever
PostgREST hands back. `/api/stores` even does `select("*")` (`server.py:127`).
That is a real inconsistency in the codebase, not a subtlety — the v2 endpoints
were built to a different standard than the pipeline ones. `/api/picks` is the
exception and is the model to follow.

### 6.2 `GET /api/picks` — determinism as a product requirement

`reachout/api/picks.py`. Fetches all stores (`id,rating` only), fetches
products with an explicit column list, then:

1. Drop anything with `stock_qty <= 0`.
2. Score each product by its **store's rating** — there is no per-shopper
   signal anywhere in the function.
3. Sort by `(-score, product_id)` — **the id is the tiebreak**
   (`picks.py:82`), so equal-rated products always order the same way.
4. Bucket by category and round-robin: at each step, prefer a category other
   than the last one emitted, then pick the best-scoring head across the
   candidate categories, tiebroken again by `(-score, id)`
   (`picks.py:95-123`).

Same database state in, same twelve products out, in the same order, every
time. **Why that matters for a recommendation surface:** this is the one place
in the consumer UI that looks like a recommender, and it contains no model, no
personalisation, and no randomness. Because it cannot personalise, the UI is
not allowed to claim it does — `PicksRail` is titled *"popular near you"*, never
*"for you"*, and there is a test pinning that. The contract enforces the same
claim from the other side: `"generated_by": {"const": "deterministic"}`.

Two defensive touches worth copying. `_PICKS_PRODUCT_FIELDS` is **duplicated**
from `server.py` rather than imported, with a comment explaining the circular
import that would otherwise occur (`picks.py:11-20`) — `server.py` imports this
module's router at line 93, before it defines `_V2_PRODUCT_FIELDS` at line 98.
And there is a **second, in-process projection** (`picks.py:62-65`) that drops
any key outside the schema's allowed set, because the test fake echoes back
whatever the fixture contains and ignores the column list. The `select()` narrows
on a real client; the projection narrows on any client.

### 6.3 Demand service — `demand/api/app.py`

| Endpoint | Params | Validated against | Notes |
|---|---|---|---|
| `GET /demand/api/health` | — | — | `{"status":"ok"}` |
| `GET /demand/api/trends` | `limit ≤ 500` | `trend_snapshot.schema.json` per row | newest first; explicit columns |
| `GET /demand/api/signals` | `window, direction, limit ≤ 500` | `demand_signal.schema.json` per row | ordered by `rank` |
| `GET /demand/api/recommendations` | `store_id` **(required uuid)**, `limit` | `recommendations_response.schema.json` | 422 on malformed uuid |
| `GET /demand/api/analytics` | `store_id` (optional uuid), `inventory_type` | `analytics_response.schema.json` | 422 on unsupported `inventory_type` |

Every read goes through `_fetch` (`app.py:202-223`), which takes a
**zero-argument callable, not a built query**. That is not style. `get_client()`
raises on a missing `SUPABASE_URL`/`SUPABASE_KEY` — the single most likely
production failure — and `client.schema(...)` / `client.table(...)` can raise
too. Before this, those calls sat outside the try/except and a misconfigured
environment produced a raw 500 with a stack trace on every route. Passing the
whole chain as a thunk leaves nowhere for that to hide.

**Two deliberate choices worth understanding:**

`/demand/api/recommendations` **requires a real `store_id`.** The response
schema requires the field and is DO-NOT-MODIFY, so the endpoint requires it too.
The previous behaviour fabricated `00000000-0000-0000-0000-000000000000` to get
past the validator — putting a store that does not exist into a response body in
order to satisfy a contract check. As `app.py:397` puts it: *"Inventing data to
pass validation is the failure the validator is there to catch."*

**5xx bodies are fixed strings.** `DB_FAILURE_DETAIL = "Database dependency
failed"`, with the real exception sent to `logger.exception` instead
(`app.py:220-222`). The driver's own message can name hosts, credentials and
SQL; this service has no auth, so "the caller" is the public. For the same
reason `_require_uuid` never echoes the rejected value back — `?store_id=<script>`
used to come back `200` with the script tag inside a body the module called
schema-validated.

### 6.4 `format` was silently unenforced, everywhere

`demand/shared/validation.py` exists because **draft-07 treats `format` as an
annotation, not an assertion.** A bare `jsonschema.validate()` accepts
`id="not-a-uuid"` against `"format": "uuid"` without a murmur. Every `format` in
every demand contract was unenforced until a `FormatChecker` was attached
explicitly.

`validate_with_formats()` is the drop-in replacement, and all demand code calls
it. It also publishes what is *actually* enforced in the current environment:

```python
UNENFORCED_FORMATS = frozenset(f for f in DEMAND_FORMATS if f not in FORMAT_CHECKER.checkers)
```

**Evaluated live on 2026-08-05, this set is empty: `uuid`, `date` and
`date-time` are all enforced.** `rfc3339-validator` is installed and is a
declared, non-optional dependency in `demand/requirements.txt`.

Three code comments still say `date-time` is unenforced — the module docstring
of `demand/shared/validation.py`, and `compute_signals.py:104-105`, and
`demand/api/app.py:24-25`. They were true when written and are now stale;
**they understate the guarantee**, which is the safe direction to be wrong in,
but they should be corrected. The defensive code they justify is still worth
keeping: `compute_signals._capture_key` (`compute_signals.py:97-115`) sorts an
unparseable `captured_at` below every real one rather than raising, which
remains the right behaviour for a value read back out of a database that has no
CHECK constraints.

The `UNENFORCED_FORMATS` mechanism is the real safeguard here, and it is a good
pattern: if that dependency ever goes missing, the set silently repopulates and
timestamps stop being checked with **nothing failing loudly to say so**. Assert
on it in a test rather than trusting a comment.

## 7. The frontend

React 19 + TypeScript + Vite, TanStack Query, react-router-dom v7, MapLibre GL.
Plain CSS with custom-property tokens — **no component library**, with one
recorded exception (D9: ECharts, confined to `components/retail/charts/`).
All copy through `src/i18n/strings.ts`. **The URL is the state of record**:
`?mode=` and `?lang=` are query params and are never persisted anywhere else.

### 7.1 The shell

`src/shell/useMode.ts` is 44 lines and worth reading in full. `parseMode`
(`useMode.ts:20`) is one line:

```ts
return raw === RETAIL_PARAM_VALUE ? "retail" : "consumer";
```

Anything that is not exactly `retail` — absent, empty, `RETAIL`, `shop`,
`retail; drop table` — is consumer. The comment gives the reason: consumer is
the half a stranger following a link should land in, and *"an unrecognised
value is not a reason to show someone a shopkeeper's dashboard."*
`setMode("consumer")` **deletes** the param rather than setting
`mode=consumer`, so there is one canonical URL per mode.

**Modes are not routes.** `main.tsx` mounts exactly two routes — `/` and
`/results` — both wrapped in `AppShell`, which is *inside* the router because it
reads `?mode=`. There is no `/dashboard` and there will not be one. Any design
doc that names `/shop` or `/dashboard` predates this decision (§10).

### 7.3 The parts that carry a rule

**`public/sw.js` — the offline cache holds the consumer app and nothing else.**
`isRetailRequest(url)` returns true for `?mode=retail` or any path under
`/demand/`, and those requests are served straight from the network with **no
cache read and no cache write**. The reason is not layout preference: a cached
dashboard would show yesterday's demand figures with nothing on screen saying
they were stale — which is the exact failure §4.10's caveat rule exists to
prevent. `manifest.webmanifest` has `start_url: "/"`, never a retail URL.

`src/pwa/sw.test.ts` reads and evaluates **the shipped file itself** via
`new Function(...)` rather than a re-implementation of its logic, so the
assertions hold for the artefact that reaches a phone. Note that `register.ts`
skips registration under `import.meta.env.DEV`, so **the PWA can only be
verified against `vite preview`, never `npm run dev`.**

**`RetailDashboard.tsx` labels practice data.** It reads `generated_from` off
the validated response and renders a visible "practice data" banner when it is
`"fixture"`. Fixture and live payloads are byte-identical in *shape* — that is
the entire point of D10 — so the only thing distinguishing them is that field,
and the UI surfaces it. When V1a lands and `generated_from` flips to `"live"`,
the banner disappears on its own. Nothing needs editing.

**`AiAnalystButton.tsx` is dead on purpose.** `disabled` *and*
`aria-disabled="true"`, no handler, no fetcher, and its reason is an on-screen
caption tied by `aria-describedby` — never a `title` tooltip, because a tooltip
is invisible on a touchscreen.

**`charts/options.ts` performs no arithmetic.** It colours a top mover by
`DIRECTION_COLOUR[p.direction]`, never by the sign of `delta_pct`, and plots
`risk_pct` and `share_pct` verbatim with no normalisation to 100. The server
computed the numbers; the browser draws them. If those two ever disagree, the
bug is one place, not two.

**`PicksRail` disappears rather than complains.** Loading, error, and empty all
render `null` — no heading, no skeleton, no reserved space. It sits beside the
search box on the landing page, and an error banner there would tell a shopper
the site is broken while the thing they came for still works.

### 7.4 What is NOT in the frontend

- **No call to `POST /api/chat`.** `ChatPanel` uses `src/chat/shopkeeper.ts`, a
  client-side mock that answers only from real search-result data passed into
  it. The backend endpoint exists and works; the UI does not use it. Swapping
  is one function body.
- **No call to `POST /api/search`.** Decision S6: the frontend is on the
  pipeline's `GET` path.
- **No call to `/demand/api/recommendations`.** Only `/analytics` is consumed.
- **No auth anywhere.** D2.

## 8. How the build itself is engineered

This repo is a system for building a system, and that is not incidental
decoration — it is why a solo operator got two backends, a demand pipeline and
a two-mode frontend built.

### 8.1 ICM — folder structure as architecture

Reference: Van Clief and McDermott, *"Interpretable Context Methodology: Folder
Structure as Agentic Architecture"*, arXiv:2603.16021 (2026).

| Layer | File(s) | Holds |
|---|---|---|
| L0 | `CLAUDE.md` | Workspace identity and rules. Read first, always. |
| L1 | `CONTEXT.md` | Routing table: which stage/module does what |
| L2 | `stages/NN/CONTEXT.md` + `prompt.md` | One stage's contract and acceptance tests |
| L3 | `_config/`, `shared/schemas/` | Cross-cutting truth. The factory. |
| L4 | `stages/NN/output/`, `data/` | Working files. The product. |

**The navigation rule:** read L0 → L1 → the **one** L2 the task names. Load
nothing else. That is the whole method — an agent that reads four files can
change one thing correctly; an agent that reads ninety files runs out of
context before it starts.

There are now **three** ICM workspaces: `reachout/`, `demand/`, and `frontend/`
(the last added by task M12 before the consumer/retail split, so the split had
somewhere to be documented).

**Why `demand/` is a separate workspace rather than a router in
`reachout/api/server.py`.** `PROJECT_OVERVIEW.md` §4.1 gives the reason
directly: *"a service whose context you can load in four files stays
changeable; one bolted into an existing tangle does not."* Concretely, it gets
its own FastAPI app, its own uvicorn process, its own Postgres schema, its own
test suite, and its own Supabase client bound to a different default schema.
The only coupling is one FK to `public.stores` and one shared `.env`. Extracting
it to its own repo later is a folder move.

### 8.2 Graph engineering

Work is a DAG executed by whatever is unblocked, not a checklist walked in
order.

- **Nodes** are tasks: Jules TASK 69–77, the UI tasks U0–U7, and the manual
  key-holding steps (M3, V1a).
- **Edges are data contracts, not prose** — a JSON Schema in `shared/schemas/`,
  or a phase flag in `SHARED_CONTRACT.md`
  (`DEMAND_INGEST_READY` → `DEMAND_API_READY` → `PICKS_READY`).
- **Parallelism is derived, not scheduled.** Anything with no unmet edge runs
  now. That is why two Jules lanes ran concurrently on separate branches, and
  why lane P (picks) never waited on lane D (demand) — they share no edge.
- **A node consumes fixtures shaped by its input schema, never another node's
  live output.** This is decision D10 and it is the single highest-leverage
  choice in the plan: it is what let the entire UI tree be built and tested
  before any Trends data existed, and it is what makes a blocked scrape a
  *content* problem rather than a *build* problem.
- **State lives on the edges, not in a conversation** — the runner's state
  JSON, the contract flags, `STATUS.md`, commit messages. Any node can fail and
  be retried without replaying the graph, which is what makes an unattended run
  restartable.
- **The runtime is a graph too**, with the same discipline: 01→05 with schema
  validation on every edge and a hard halt on failure, and the demand chain
  built the same way.

**The honest critique.** The machine-readable state held; the human-readable
state did not. All seven `SHARED_CONTRACT.md` flags are correctly `[x]` and
match the code. But `docs/TRACKER.md` was **five finished tasks behind reality**
until commit `30def57`, and before the merge each work branch only ticked its
own flags — so neither branch alone showed the true state.

The implication for a new engineer is precise: **trust the flags and the code;
verify the board.** The flags are single-line, single-writer, and touched by the
task that satisfies them. The board is prose maintained by a human-facing
process, and prose drifts. §10 lists the specific files that are wrong right
now.

### 8.3 The offload model

| Who | Takes | Why |
|---|---|---|
| **Strong models** (Opus/Fable, orchestrating session) | Planning, JSON Schemas, SQL DDL, anything touching live keys, merge review, the UI tasks | The expensive model should spend tokens on contracts and review, not on typing |
| **Jules** (async coding agent on VMs) | Small, single-concern, offline-testable backend tasks | Its VMs hold **no keys** — which is *why* every task must pass on fakes and fixtures |
| **Stitch** | Design specs only | **There is no Stitch API.** Google Stitch is a browser tool. |

The Stitch point is the one that trips people, because three documents are
written as if an API exists. Verified by grep: `stitch` appears in **zero**
`.py`/`.ts`/`.tsx`/`.json`/`.toml`/`.yaml` files in this repo — every mention is
markdown. The v1 "fallback" (the coding agent implements each prompt directly)
was always the real path and is now the only path. The specs are still good UI
specs; they are bad API contracts.

The Jules constraint is the load-bearing one. **Because Jules VMs hold no keys
and no live dependencies, every task must be green on fixtures alone.** That
single constraint is why `trendspy`/`pandas` are lazy-imported (§4.2), why
`load_dotenv` on a missing file is a no-op (§4.12), why both test suites ship
their own chainable fake Supabase client (`demand/tests/fake_supa.py`,
`reachout/tests/fake_supa.py`), and why `demand/tests/test_fake_supa_fidelity.py`
exists at all — a fake that drifts from the real client turns a green suite into
a lie.

### 8.4 `tools/jules_runner.py`

735 lines. Submits tasks from a markdown fuel file to the Jules API, one session
each, and merges each result back through a git worktree (no `gh` CLI needed).

The parts that matter:

**The merge is a gate, not a push.** Before anything reaches `origin`, the
resolved test command runs in-worktree via `subprocess`. A non-zero exit leaves
the task `"pending"` in state (never `"done"`), logs the output tail, and
**stops the run outright** — no further tasks attempted, nothing pushed. Only a
green suite reaches the integration branch, so the next task always builds on
tested work.

**`--promote-main` is opt-in.** Default is off: work stays on the integration
branch. v1's behaviour was to auto-promote every completed task to `main` with
no test gate and nobody looking; reproducing that now requires passing the flag
explicitly. This preserves D5's reversal path while making the unsafe thing the
one you have to ask for.

**Lane isolation.** Each concurrent lane gets its own `--branch`, `--state`, and
worktree. The state file is protected by a PID lock file created via temp-file +
`os.link` (not `O_CREAT|O_EXCL`, so it is never observable in an unpopulated
state). Stale locks whose PID is dead are detected, removed, logged, and
retried. A runner only ever removes a lock still naming its own PID.

**The trap the runner documents against itself** (`jules_runner.py:72-80`):
`--tasks` is a *shared* file, so two lanes fed the same tasks file resolve the
`<!-- TEST_CMD: ... -->` header to the **same command** regardless of which task
each lane is running. A lane whose code lives outside what that header tests —
e.g. lane P writing only in `reachout/` while the header points at `cd demand
&& pytest` — passes a gate having tested nothing. Any such lane must pass its
own `--test-cmd`. This is exactly the defect the CLI > file > default precedence
chain exists to prevent, and it is documented rather than fixed, which is the
right call for a build-time tool.

**Lanes were a build-time device.** The repo has since consolidated onto `main`
(`4d0dd05`, `df9b36e`). The runner still works; there is nothing left for it to
run.

single real trend.** The dashboard renders the committed fixture and says
"practice data" on screen. That is the honest state, and the UI is built so that
